【四、为什么 Socket 直连能防抓包？】
================================================================================

普通 App 使用 NSURLSession 的流量路径：

  App → NSURLSession → 系统网络栈 → [系统代理拦截] → 服务器

778.ipa 使用 httplib 的流量路径：

  App → httplib(C++) → socket() → connect() → 直连服务器

关键区别：
  · Charles/Proxyman/mitmproxy 等抓包工具只能代理系统网络栈（NSURLSession）
  · httplib 使用底层 POSIX socket API，完全绕过了系统网络层
  · 抓包工具无法 hook 到 httplib 的内部网络调用
  · 即使设置了系统 HTTP 代理，对底层 socket 也完全无效

【八、778.ipa 的优势与不足】
================================================================================

✅ 优势：
  1. 使用底层 socket 直连，彻底绕过系统代理（核心优势）
  2. 自定义加密层（MyEncrypt/MyDecrypt），增加逆向难度
  3. AES-CBC 加密传输数据，保证传输安全
  4. SSL Pinning 防止中间人证书替换
  5. 定时自动验证，防止长期离线使用
  6. VPN/代理接口检测，主动发现抓包环境

❌ 不足：
  1. 下载直链明文写在代码中（http://111.170.18.181:49110/...）
  2. 没有请求签名机制（无 HMAC/RSA），无法防重放攻击
  3. API 域名明文可见（虽然用了 Punycode 编码）
  4. 编译路径暴露开发者信息（/Users/hby/...）


【九、可借鉴的技术点（移植建议）】
================================================================================

如果需要将 778.ipa 的防抓包方案移植到 PersonalCenterUI 项目：

  方案 A（推荐 - 低风险）：
    · 保持现有 NSURLSession 架构
    · 将下载直链改为从服务端 API 动态获取（加密传输）
    · 加上 URL 过期机制（服务端下发临时签名 URL）
    · 优点：改动小，兼容性好，防护足够

  方案 B（中等风险）：
    · 引入 httplib C++ 库用于验证请求
    · 保持 NSURLSession 用于文件下载（下载量大时 socket 不稳定）
    · 验证请求走底层 socket，彻底防代理
    · 优点：验证流量完全防抓包，下载流量仍可用代理

  方案 C（高风险）：
    · 全部改用 httplib socket 直连
    · 验证 + 下载 + 心跳全部走底层 socket
    · 优点：最强防护
    · 缺点：代码改动大，需处理 HTTPS/TLS 握手，iOS 适配复杂
